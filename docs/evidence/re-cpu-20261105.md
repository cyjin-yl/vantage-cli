## 3. Rated clocks: two firmware numbers, neither is "current"

| value | MHz | meaning bound to the source |
|---|---|---|
| registry `~MHz` | 3686 | the firmware's approximate processor frequency; a **rated** value, never a live measurement |
| `Win32_Processor.MaxClockSpeed` | 1900 | the firmware-declared maximum rated clock |
| Intel published spec (external, not measured here) | 1900 base / 4.8 GHz max turbo | `https://www.intel.com/content/www/us/en/products/sku/245527/intel-core-ultra-x7-processor-358h-18m-cache-up-to-4-80-ghz/specifications.html` lists "up to 4.80 GHz"; the third-party database `techpowerup.com/cpu-specs/core-ultra-x7-358h.c4304` lists 1900 MHz base, E-core 1500 MHz → 3.5 GHz |

Two conclusions the implementation must respect:

1. **`MaxClockSpeed` is the P-core rated clock, not a ceiling.** It equals the
   published 1900 MHz base. No Windows channel on this machine exposes the
   4.8 GHz turbo ceiling, so `cpu status` never reports a "max" number for it.
2. **The registry `~MHz` value cannot be repaired into a known quantity.** It is
   neither the 1900 MHz base nor the 4.8 GHz turbo ceiling, and nothing on the
   machine explains 3686. It is therefore reported verbatim as a
   firmware-declared approximate clock, labelled as such, and never used as a
   current clock or as a multiplier.

## 4. Current clock: derived from the documented performance counter

### 4.1 Class shape

`SELECT Name, ProcessorFrequency, PercentProcessorPerformance, PercentPerformanceLimit
FROM Win32_PerfFormattedData_Counters_ProcessorInformation` returns **18**
instances: 16 logical-CPU rows named `0,<index>` plus the two aggregates
`_Total` and `0,_Total`. Only the `0,<index>` rows are per-logical-processor
observations; both aggregate names must be excluded (they contain a
non-numeric field).

`ProcessorFrequency` is the rated clock the counter normalizes its percentage
against; `PercentProcessorPerformance` is the documented "average performance
of the processor relative to nominal frequency" counter, so the live clock is

```
current_clock_mhz = ProcessorFrequency × PercentProcessorPerformance / 100
```

— the same derivation the OS's own task manager performs. The percentage is
what moves; it exceeds 100 under turbo, which is exactly why the product, and
not `ProcessorFrequency`, is the current clock.

Every derived value stays under the published per-cluster ceilings (P-core
1900 → 3382 MHz vs 4.8 GHz; E-core 1500 → 3045 MHz vs 3.5 GHz), and the turbo
percentage is unambiguous: a core at `203 %` of 1500 MHz is not running at
1500 MHz. `PercentProcessorPerformance` is clearly live — it moves between
samples and rises under load.

Observed precision limits, which the output must state rather than hide:

* the class is a **1-second snapshot** and a core with no non-idle work reports
  `0 %`, i.e. no frequency information at all (idle C-state, not 0 MHz);
* the rated reference is not pinned: the P cluster reported `1809` and `1900`
  in different samples (≈5 %), so the derived value carries that much jitter
  plus percent quantization (1 % of 1500 ≈ 15 MHz).

### 4.3 Mapping logical processors to clock domains

The rated reference splits the package into two domains, which is the hybrid
topology: `0..3` at 1900 MHz (the four P-cores: `NumberOfCores` 16 with 4 P +
12 E per the published configuration) and `4..15` at 1500 MHz (the E/LP-E
cores). `cpu status` therefore groups logical CPUs by their observed rated
clock rather than inventing a P/E label, because neither the counter nor
`Win32_Processor` names the core type.

## 5. Rejected current-clock sources

### 5.1 `CallNtPowerInformation(ProcessorInformation)`

Returns 16 entries (`PROCESSOR_POWER_INFORMATION`). Sample 1:
`MaxMhz=1900, CurrentMhz=1900, MhzLimit=1900` for `cpu0..3` and
`MaxMhz=1500, CurrentMhz=1500` for `cpu4..15`; after 1 s, `cpu1..3` read
`CurrentMhz=1809`. `CurrentMhz` never exceeds the rated clock, it is quantized
to the same 1809/1900/1500 ladder, and it does not move while the performance
counter simultaneously reads `135 %`–`210 %`. This API reports the P-state
nominal frequency, not the turbo frequency; using it as `current_clock` would
publish 1900 MHz on a core measured at 2565–3382 MHz.

### 5.2 `Win32_Processor.CurrentClockSpeed`

`1900` in every sample, identical to `MaxClockSpeed`, and unchanged between an
idle machine and the load sample. It is a static firmware value on this SKU.

`MaximumMHz`/`MHz`-style firmware-declared values are not used as current
clocks either; `MaxClockSpeed` is reported only under its
firmware-declared-rated label (§3), and `CurrentClockSpeed` is omitted.

### 5.3 MSR `0x198`

`IA32_PERF_STATUS` would give the actual per-core ratio, but the only MSR
transport is `\\.\WinMsrDev`, and `CreateFileW` on it returns err 5
(ACCESS_DENIED) from this SSH network logon; the driver's six-selector
whitelist does not include `0x198` in any case. See
`docs/evidence/wmi-capability-exhaustion-20261104.md` §10. Not implemented.

## 6. EPP and boost from the documented power API

`PowerReadACValueIndex` / `PowerReadDCValueIndex` against the active scheme
(`381b4222-…`, balanced), subgroup `54533251-82be-4824-96c1-47b60b740d00`:

| setting | GUID | AC | DC | `PowerReadValueMin/Max/Increment` |
|---|---|---|---|---|
| `PERFBOOSTMODE` | `be337238-0d82-4146-a960-4f3749d470c7` | `2` | `2` | status **2** (`ERROR_FILE_NOT_FOUND`) for all three — no bounds advertised |
| `PERFEPP` | `36687f9e-e3a5-4dbf-b1dc-15eb381c6863` | `50` | `50` | `0` / `100` / `1` (status 0) |
| `PROCTHROTTLEMAX` | `bc5038f7-23e0-4960-96da-33abaf5935ec` | `100` | `100` | `0` / `100` / `1` (status 0) |
| `PROCTHROTTLEMIN` | `893dee8e-2bef-41e0-89c6-b55d0929964c` | `5` | `5` | `0` / `100` / `1` (status 0) |

* `2` is `ProcessorBoostMode::AGGRESSIVE` (index, a value the existing
  `PERFBOOSTMODE` type preserves as an index rather than as a boolean).
* `powercfg /q SCHEME_CURRENT SUB_PROCESSOR` lists only `PROCTHROTTLEMIN` and
  `PROCTHROTTLEMAX`; `PERFBOOSTMODE` and `PERFEPP` are hidden settings, yet
  `PowerRead*ValueIndex` reads both with status 0. So `powercfg` is not an
  availability test for them — the CLI reads them through `PowerRead*`.
* `PERFBOOSTMODE` advertises **no** numeric range on this SKU. Any range shown
  for it must be `Unavailable` with the API's own error text, never a
  synthesized `0..=4`. `cpu status` reports each range exactly as
  `PowerReadValue{Min,Max,Increment}` returns it, so on this target `epp_range`
  is `available 0..=100 increment 1` and `boost_range` is
  `unavailable (ERROR_FILE_NOT_FOUND)`.

## 7. Implementation contract

`vantage cpu status` (read-only, no arguments, one CIM query pair + one
registry read per invocation):

| output field | source | rule |
|---|---|---|
| `name` | `Win32_Processor.Name`, else registry `ProcessorNameString` | absent if both missing |
| `vendor` | registry `VendorIdentifier`, else `Win32_Processor.Manufacturer` | absent if both missing |
| `identifier` | registry `Identifier` (CPU family/model/stepping text) | absent if unreadable |
| `cores`, `threads` | `NumberOfCores`, `NumberOfLogicalProcessors` | absent if unreadable |
| `firmware_max_clock_mhz` | `Win32_Processor.MaxClockSpeed` | labelled rated/firmware-declared; never current |
| `firmware_approximate_clock_mhz` | registry `~MHz` | labelled rated/firmware-declared; never current |
| `l2_cache_kb`, `l3_cache_kb` | `Win32_Processor.L2CacheSize`, `L3CacheSize` | absent if unreadable |
| `clusters[]` | performance-counter rows grouped by `ProcessorFrequency` | `rated_clock_mhz`, `logical_processors`, `percent_processor_performance` (max of the group), `current_clock_mhz` = rated × pct / 100 |
| `current_clock_mhz` | max over clusters | **derived**, `null` when no cluster had a positive percentage |
| `current_clock_source` | fixed | `processor_performance_counter` |
| `current_clock_availability` | derived | `available` when ≥1 positive sample; `limited` when rows exist but every percentage is `0`; `unavailable` when the class query failed or returned no per-core row |
| `current_clock_detail` | — | the failure/zero-sample reason when availability is not `available` |
| `epp_percent` | `PowerRead{AC,DC}ValueIndex` `PERFEPP` | AC/DC integers |
| `boost_mode` | `PowerRead{AC,DC}ValueIndex` `PERFBOOSTMODE` | AC/DC `ProcessorBoostMode` indices |
| `epp_range` | `PowerReadValue{Min,Max,Increment}` `PERFEPP` | `available {min,max,increment}` or `unavailable {detail}`; never a synthesized bound |
| `boost_range` | `PowerReadValue{Min,Max,Increment}` `PERFBOOSTMODE` | same shape; `unavailable` on this SKU |

Rules that follow from the evidence:

* the derived clock is never replaced by a rated value when the counter is
  missing — availability becomes `unavailable` and the value stays `null`;
* a cluster whose percentage is `0` contributes no derived clock; the group is
  still reported with its rated clock so the zero is visible;
* `CurrentClockSpeed`, `CallNtPowerInformation` and MSR values are not fields of
  the payload at all.
* `PROCTHROTTLEMIN`/`PROCTHROTTLEMAX` are recovered in §6 and readable through
  the same `PowerRead*` calls, but this command does not export them: they are
  already owned by `power saver-once`, which reads and restores
  `PROCTHROTTLEMAX` as part of its own transaction
  (`crates/vantage-cli/src/lib.rs`, `execute_power_saver_once`). Adding a second
  reader here is a follow-up decision for the parent, not something this
  document silently drops.
