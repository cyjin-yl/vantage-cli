# Fan-speed readability on ThinkBook 21VG — the answer is no, and here is every channel — 2026-11-06

Target: `TB14P-EZRA` (ThinkBook 21VG, Panther Lake), user `ezra`, elevated session.
All probes are **read-only**: no `SetSmartFanMode`, no `SetFanCooling`, no `Fan_Set_Table`,
no `KBLC` set argument, no registry write. `\\.\EnergyDrv` is opened with `GENERIC_READ` only.

Question this document answers: **is fan speed (a live RPM/tach) readable on this SKU now
that the fan write path is dead?** Answer: **no.** No interface on this machine returns a
current fan speed. What exists is a static per-fan RPM *range* (`2100..5100`) plus absent
fan-table/fan-limit classes. Consequently no `perf fan rpm` command is added.

## 4. `LENOVO_FAN_TABLE_DATA`, `LENOVO_FAN_MAX_SPEED_DATA`, `LENOVO_FAN_METHOD` — absent

All three classes are *registered* in `root\wmi` and publish schemas, and all three answer
nothing:

| class | declared properties (excerpt) | instance query |
|---|---|---|
| `LENOVO_FAN_MAX_SPEED_DATA` | `Fan_Id:UInt8`, `Fan_CurrentMaxSpeed:UInt16`, `Fan_DefaultMaxSpeed:UInt16`, `Fan_Flag:UInt8` | `不支持` (`WBEM_E_NOT_SUPPORTED`) |
| `LENOVO_FAN_TABLE_DATA` (19 props) | `Fan_Id:UInt16`, `Mode:UInt16`, `FanSpeedStep:UInt16`, `FanTable_Data:UInt16Array`, `FanTable_Len:UInt32`, `Sensor_ID:UInt32`, `SensorTable_Data:UInt16Array`, `CurrentFanMinSpeed/CurrentFanMaxSpeed`, step and temperature thresholds | `不支持` |
| `LENOVO_FAN_METHOD` | methods only (`Fan_Get_Table`, `Fan_Set_Table`) | `不支持` (no instance) |

```
  -> FanTable: UInt32Array [ID,out,WmiSizeIs], FanTableSize: UInt32 [ID,out],

Fan_Set_Table(FanTable: UInt8Array [ID,in,Max])
```

Invocation matrix for the **getter** (nothing was written):

| attempt | result |
|---|---|
| `Invoke-CimMethod … -Arguments @{FanID=[uint16]1;SensorID=[uint16]0}` | client-side `参数"SensorID"的类型不匹配` |
| `… [uint32]/[uint32]` | client-side type mismatch |
| `… [byte]/[byte]` (the declared type) | `0x8004102F` `WBEM_E_INVALID_METHOD_PARAMETERS` |
| `… @{FanID=1}` (SensorID omitted) | client-side type mismatch on `FanID` |
| SWbem class `ExecMethod_` with spawned in-parameters | `0x8004102F` |
| `Get-CimInstance LENOVO_FAN_METHOD` | `不支持` |

So the method plane is unreachable for two independent reasons: the class exposes no instance
(the ACPI-WMI mapper reports the whole class unsupported on this firmware), and the class-scope
exec is rejected. Even a positive answer would have been a **fan curve table** (step →
RPM/threshold pairs) and a per-fan **maximum-speed limit**, not a measured current speed.

## 6. ACPI thermal zone: active trip points are policy, not speed

`MSAcpi_ThermalZoneTemperature`, instance `ACPI\ThermalZone\TZ00_0`:

```
ActiveTripPointCount = 5
ActiveTripPoint      = [3732, 3282, 3232, 3182, 3132]   (100.05, 55.05, 50.05, 45.05, 40.05 °C)
CriticalTripPoint    = 3782                              (105.05 °C)
PassiveTripPoint     = 0
CurrentTemperature   = 3192 (46.05 °C) in all seven samples between 09:03 and 10:33
```

The active trip points are the firmware's cooling-policy thresholds — the temperature steps at
which it may raise cooling — and identical across every sample. They are not a fan speed, and
they did not change while the ESIF participants rose from 51 to 69 °C. The zone's own
`CurrentTemperature` also stayed at `3192` for ~90 minutes; that is recorded as an observation
about this firmware zone's update granularity, **not** as a frozen sensor (the same class moved
between 3162 and 3242 on 2026-11-05, `docs/evidence/re-thermal-20261105.md` §2).

## 7. EnergyDrv: the `KBL*` family answers, and it is keyboard-backlight data

Transport was proven before any conclusion was drawn from an `ERR`:

```
open \\.\EnergyDrv GENERIC_READ          -> handle valid, err=0
IOCTL 0x83102144 (KBLC) arg=0x1          -> OK 07 00 00 00      # documented live value 0x7
IOCTL 0x831020f8 (GBMD) in=0xFF          -> OK 04 00 86 00      # 0x00860004, matches docs
```

The two unrecovered family members, probed read-only (no argument with a `set` nibble):

| IOCTL | arg `0x0` | arg `0x1` | arg `0x2` |
|---|---|---|---|
| `0x83102154` KBLR | `0x00000000` | `0x00000003` | `0x00000001` |
| `0x83102158` KBLA | `0x00000000` | `0x00000003` | `0x00000003` |

Three rounds at 10:32–10:33 (CPU load 40 → 84 → 85 %, ESIF max 50 → 56 → 69 °C) returned the
same values in every round — `KBLC(1)=0x7`, `KBLR(1)=0x3`, `KBLR(2)=0x1`, `KBLA(1)=0x3`,
`KBLA(2)=0x3`, `SMTF=0x0000FFFF`. The `arg=0` column was sampled once per code, in the 10:28
run (`fanrpm-w9b`). So:

* both codes **do answer** — they are live vendor IOCTLs, not dead codes;
* their reply domain is `{0,1,2,3}`, which is exactly the keyboard-backlight state domain
  (`KBLC` query → `0x7` = tristate+auto ⇒ states 0..3), **not** an RPM domain;
* `KBLR`/`KBLA` are keyboard-backlight reads (current level / ambient-auto state, per the
  `KBL` = keyboard-backlight naming in `docs/interfaces.md` §11.8) — **[INFERENCE]** on which
  of the two carries which, since a `set` argument would be needed to separate them and this
  probe is read-only;
* they do not move with thermal load, which a fan tach would.

Two further negative datapoints from the same handle:

```
IOCTL 0x831020c4 (generic GET) in=0x83102144 / 0x83102154 / 0x83102158
        -> ERR 87 (ERROR_INVALID_PARAMETER)   # selector not in the driver's allowlist
IOCTL 0x8310212c (SMTF) arg=0
        -> OK ff ff 00 00                     # 0x0000FFFF unsupported sentinel, constant
```

Structural confirmation that the vendor driver carries no fan method at all: a byte scan of
`AcpiVpc.sys` 15.11.30.14 (52800 bytes, driver store `acpivpc.inf_amd64_07db38bc9e02b27d`)
finds **no** `Fan`, `RPM`, `Tach`, `FTST`, `FANG`, `FSL` token in either ASCII or UTF-16; the
only four-character token containing `F` is `INFO`. `acpi.sys` yields only `INFO`, `MOFD`,
`MOFR`. The virtual-power-controller IOCTL surface therefore cannot forward a fan ACPI method
— the EC fan tach, if the EC has one, is not reachable through it.

## 11. Decision

* **No `perf fan rpm` command is added.** No channel returns a current fan speed, and the
  command surface must not manufacture one from `FanMinSpeed`/`FanMaxSpeed` (a configured
  range) or from `Fan_CurrentMaxSpeed` (a limit, absent on this SKU anyway).
* `perf fan status` stays as it is: fan mode (firmware readback, else the `ITS_FanMode`
  dispatcher projection) plus the fan inventory record from `LENOVO_FAN_TEST_DATA`. Its JSON
  must keep carrying only `min_rpm`/`max_rpm` per fan — never a `rpm`/`current speed` key.
* `WindowsThermal::fans()` / `fan_table()` need no change: inventory is what the firmware
  publishes, and `perf.fan.curve` stays `Unsupported` (`LENOVO_FAN_METHOD` + `LENOVO_FAN_TABLE_DATA`
  are both `不支持`).
* No capability id changes: `perf.fan.status|auto|manual|fullspeed|smart|curve` exist;
  `perf.fan.inventory` and `perf.fan.mode(.write)` are recorded by the probe. There is and
  should be no `perf.fan.rpm` row.
* Side observation for its own owner: `lctrl-tune`'s profile `Constraints` block carries
  `fan_rpm_max` (and `temp_max_c`, `battery_only`, `min_dwell_s`) but no code consults the
  struct — so a constraint that cannot be read on this SKU is also never evaluated. That is a
  `lctrl-tune` question, not a fan-channel question, and is not changed here; if an evaluator
  is added it must report "unreadable"/refuse rather than treat an absent read as satisfied.

## 12. Inference register and limits

| claim | status |
|---|---|
| `FanMinSpeed`/`FanMaxSpeed` are configured RPM bounds, not measurements | observed (schema has no current-speed property; values never moved across 7 samples / +19 °C) |
| `KBLR` = current backlight level, `KBLA` = ambient/auto state | **[INFERENCE]** from the `{0..3}` reply domain matching the `KBLC` state domain and the `KBL` naming in `docs/interfaces.md` §11.8; separating them needs a `set`, which this probe does not do |
| `ActiveTripPoint` is a cooling-policy threshold | standard ACPI semantics of the class; the array is constant here, which is what a policy table does |
| `TZ00` stayed at 3192 for ~90 min because the zone updates coarsely | **[INFERENCE]**; the same class moved on 2026-11-05, so it is not a frozen sensor. Not load-bearing for this document |
| "Fan speed is not readable" | scoped to the interfaces probed: every class in `root\wmi` (1650, property-name scan) incl. the fan/GAMEZONE/ESIF classes, `Win32_Fan`/cimv2 cooling, ACPI thermal zone, `PNP0C0B` device properties, `\\.\EnergyDrv` VPC IOCTLs (whole family), `root\Lenovo` (absent) |
| the EC may still have a tach the platform never exposes | open. Absence of a channel is not proof the controller measures nothing; it is proof that nothing user-reachable on this SKU reports it |

Additional limit: the load tests were CPU-only PowerShell burn jobs. Package temperatures rose
to 69 °C, still 31 °C below the 100 °C active trip point, so **no fan ramp is proven to have
happened**. The static-versus-tach argument does not depend on a ramp: no candidate ever
returned a numeric current-speed value at all, and the only answering non-inventory channel
(the `KBL*` family) stayed inside a 4-value state domain.
