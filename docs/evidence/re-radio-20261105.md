# Radio / airplane-mode channel — owner recovery and `radio` contract — 2026-11-05

Target: `TB14P-EZRA` / LENOVO 21VG (ThinkBook 14 G8+ IPH), Windows 11 Pro for
Workstations 10.0.26300, firmware `SWCN22WW`.
Scope: `radio status` (read-only: Wi-Fi / Bluetooth / mobile-broadband soft + hard state) and
the reversible write `radio off|on`.

This document was written **before** the implementation, per the wave method: contract first,
then code that only covers what the live channel actually exposes.

## 1. Verdict: the owner is the WinRT Radio API

| candidate owner | result on this SKU |
|---|---|
| Lenovo WMI flight-mode class | **does not exist.** Full `root\WMI` `Lenovo_*` enumeration = 60 classes (`LENOVO_*_DATA`, `LENOVO_*_EVENT`, `Lenovo_BiosSetting`, `Lenovo_FunctionRequest`, …) — none is a radio/airplane/flight class. A class-name filter for `Radio|Flight|Airplane|Wireless|WWAN` over `root\WMI` returns exactly one class, `SystemConfig_V2_FlightIds` (a setup/configuration class, unrelated). `root\CIMV2` returns only `Win32_PerfRawData_Counters_BluetoothRadio` / `…FormattedData…`, which are performance counters and carry no radio state. |
| EnergyDrv (`\\.\EnergyDrv`) | **not a radio channel.** Its documented plane on this SKU is battery/charge (`docs/evidence/re-battery-adv-20261105.md`); no radio verb exists in that contract. |
| **WinRT `Windows.Devices.Radios.Radio`** | **owner.** `RequestAccessAsync` → `Allowed`; `GetRadiosAsync` enumerates the machine's radios. |

Underneath the WinRT projection sits the operating system's radio-management plane:
`HKLM\SYSTEM\CurrentControlSet\Control\RadioManagement` registers one radio manager per media —
`{833A69FB-5E17-4893-85A5-1EF469217372}` → `WlanRadioManager.dll`,
`{1910E202-236A-43E6-9469-FE0B3149F3D9}` → `WwanRadioManager.dll`,
`{3F9FF9AB-AC3E-40BB-BBC9-27B648AD1FB2}` → `XboxGipRadioManager.dll`, and
`{afd198ac-5f30-4e89-a789-5ddf60a69366}` → `…\BluetoothRadioState`.

Vendor-side confirmation that Lenovo code drives **that** plane and not a private one
(ASCII + UTF-16 string scan of the Vantage addins and `C:\Program Files\Lenovo`, files < 12 MB):

| binary | matching signatures |
|---|---|
| `…\Addins\SEDiagnosisAddin\1.0.7.122\SEDiagnosis.dll` | `FlightMode`, `RadioManagement`, `RadioState`, `SystemRadioState` |
| `…\Addins\SmartDisplayAddin\1.0.2.623\x64\SESmartWireless.dll` | `RadioManagement`, `RadioState`, `SystemRadioState` |
| `…\Addins\SmartNoiseCancelledAddin\1.3.1.97\EarphoneTWS.dll` | `Windows.Devices.Radios` |
| `C:\Program Files\Lenovo\Ready For Assistant\iOSPlugin\iOSPlugin.exe` | `RadioState`, `Windows.Devices.Radios` |
| `…\VantageService\5.1.2609.9\Vanara.PInvoke.WlanApi.dll`, `…\VantageCoreAddin\1.1.0.67\Vanara.PInvoke.WlanApi.dll` | `RadioState` (WLAN API P/Invoke surface) |

So there is **no Lenovo binary to reverse for a radio setter**: the vendor binaries reference the
same OS plane (WinRT `Windows.Devices.Radios` / `RadioManagement` / WLAN API) that this
implementation calls. [INFERENCE] The observed `FlightMode` string in `SEDiagnosis.dll` is a
diagnostic *reader* of the airplane-mode state; no write to a vendor radio object was observed.

## 2. Live receipts

All observations 2026-11-05 on the target over the running session. Read-only unless marked.

### 2.1 WinRT enumeration (read-only)

```

  kind=Bluetooth  state=On  name=蓝牙
```

No `MobileBroadband` and no `FM` radio is enumerated. Independent confirmation that this SKU has

### 2.2 Documented reversible write, proven on the Bluetooth radio

`Radio.SetStateAsync` was exercised on the **Bluetooth** radio (the only radio whose disablement
cannot cut the session; see §5). Read-back came from two independent sources — a fresh
`GetRadiosAsync` enumeration and PnP device state:

```
BEFORE   Bluetooth state=On    WiFi state=On          PnP Bluetooth OK nodes = 38
setOff   status=Allowed  elapsed=74 ms
OFF      Bluetooth state=Off   WiFi state=On          PnP Bluetooth OK nodes = 2
immediate_state=Off   after3s_sameobject_state=Off     bthserv=Running
setOn    status=Allowed  elapsed=11689 ms
RESTORED Bluetooth state=On    WiFi state=On          PnP Bluetooth OK nodes = 38
```

Findings that the implementation depends on:

- `SetStateAsync` is honoured from a **non-packaged desktop process**; the returned
  `RadioAccessStatus` was `Allowed` (the access status is a per-application radio consent, not an
  administrator check).
- Bring-up of the Bluetooth radio stack takes **≈ 11.7 s**, while teardown is ≈ 74 ms. The await
  window must be generous (the implementation allows 60 s) and read-back must tolerate a long
  transition instead of failing after a few polls.
- The state read back from the same `Radio` object and from a fresh enumeration agreed, and the
  Bluetooth stack's PnP node set came back to its original size — the write is real and reversible.

### 2.3 Wi-Fi per-PHY soft/hard state (`wlanapi!WlanQueryInterface`)

```
WlanOpenHandle(client 2) -> rc=0 negotiated=2
WlanEnumInterfaces       -> rc=0 interfaces=1
  guid=a281055e-60b2-4bc5-89dc-d1b6bbca7712  state=0 (not_ready)
  WlanQueryInterface(opcode 4 = wlan_intf_opcode_radio_state) -> rc=0 size=772 vtype=2
    dwNumberOfPhys=7
    phy[0..6]  software=1 (dot11_radio_state_on)  hardware=1 (dot11_radio_state_on)
  WlanQueryInterface(opcode 6 = wlan_intf_opcode_interface_state) -> rc=0 size=4 value=1 (connected)
```

Two layout facts worth recording because a naive parse gets them wrong:

- The returned buffer size is the **fixed struct size**, `4 + 64*12 = 772`, not
  `4 + dwNumberOfPhys*12` (7 PHYs were reported inside a 772-byte buffer). The parser must read
  `dwNumberOfPhys`, bound it to 64, and require `size >= 4 + n*12`.
- `wlan_intf_opcode_radio_state` is opcode **4** and returns `WLAN_RADIO_STATE`
  (`{ u32 dwNumberOfPhys; WLAN_PHY_RADIO_STATE[64] }`, each PHY `{ u32 dwPhyIndex; i32
  dot11SoftwareRadioState; i32 dot11HardwareRadioState }`). `dot11_radio_state_on = 1`,
  `off = 2`, `unknown = 0`.

This is the only documented source of the **soft vs hard** distinction for Wi-Fi. The WinRT
`Radio.State` value is an aggregate (`On`/`Off`/`Disabled`/`Unknown`) and cannot separate a
software-off from a hardware-gated radio; the WLAN API can.

### 2.5 The exact ABI the implementation calls, validated live

Because the Rust code is hand-written COM (no `windows` crate dependency is added), the recovered
layout was exercised end-to-end from a raw ABI probe on the target before the module was written:

```
RoInitialize(MTA)                       hr=0x80010106  (RPC_E_CHANGED_MODE: host already in an STA)
WindowsCreateString("Windows.Devices.Radios.Radio")  hr=0
RoGetActivationFactory(IRadioStatics)   hr=0            factory RuntimeClassName = hr=0x8000000E
RequestAccessAsync (slot 9)             hr=0            await: poll IAsyncInfo.get_Status -> Completed
  GetResults (slot 8)                   access=1        (Allowed)
GetRadiosAsync    (slot 6)              hr=0
  GetResults -> view RuntimeClassName = Windows.Foundation.Collections.IVectorView`1<Windows.Devices.Radios.Radio>
  get_Size (slot 7) = 2 ; GetAt (slot 6) hr=0 for both
  element RuntimeClassName = Windows.Devices.Radios.Radio ; QI(IRadio 252118DF-…) hr=0
  get_Kind (11) / get_State (9) / get_Name (10): kind=3 state=1 蓝牙, kind=1 state=1 WLAN
SetStateAsync (slot 6, Off=2) hr=0 ; await status=1 polls=4 elapsed~60 ms ; GetResults value=1
  state read-back 1 -> 2 ; SetStateAsync (On=1) hr=0 ; await polls=26 ; state 2 -> 1
```

Three findings changed the implementation:

1. `RoInitialize(RO_INIT_MULTITHREADED)` returns `0x80010106` when the host thread already lives in
   an apartment. That is tolerated, and such an apartment is never uninitialized.
2. The **activation factory rejects `IInspectable::GetRuntimeClassName`** with
   `0x8000000E` (`E_ILLEGAL_METHOD_CALL`). A factory identity check would therefore have produced a
   fail-closed *false negative*; identity is asserted on the radio elements and on the returned
   collection shape instead.
3. `WlanQueryInterface` sizes reported by the service, `IP_ADAPTER_ADDRESSES_LH` field layout
   (`Length` 0 / `IfIndex` 4, `IfType` 100, `OperStatus` 104, `Description` 64, `FirstGatewayAddress`
   208, unicast `Next` at +8 and `SOCKET_ADDRESS` at +16) and
   `GAA_FLAG_INCLUDE_GATEWAYS` populating the Wi-Fi adapter's gateway were all confirmed against
   live data, including the 448-byte struct length.

| candidate | evidence |
|---|---|

| `netsh wlan show interfaces` | on build 26300 the output has `State : connected` but **no** `Radio status` lines, so it cannot supply soft/hard radio state. (It remains valid for SSID/BSSID/signal, which is what `wifi security` uses it for.) |
| `Win32_PerfRawData_Counters_BluetoothRadio` | exists, but it is a performance-counter class with no on/off state. |

## 4. Implemented plane

`crates/lctrl-hal-win/src/radio.rs` calls only these documented interfaces, with a deliberately
minimal vtable surface (every HRESULT checked, every `HSTRING`/`IUnknown` released):

- `combase.dll`: `RoInitialize`/`RoUninitialize`, `WindowsCreateString`/`WindowsDeleteString`/
  `WindowsGetStringRawBuffer`, `RoGetActivationFactory`.
- `IRadioStatics` `{5FB6A12E-67CB-46AE-AAE9-65919F86EFF4}` — slots used: `GetRadiosAsync` (6),
  `RequestAccessAsync` (9). `IRadio` `{252118DF-B33E-416A-875F-1CF38AE2D83E}` — slots used:
  `SetStateAsync` (6), `get_State` (9), `get_Name` (10), `get_Kind` (11).
- `IAsyncOperation<T>` (base `IInspectable` + `SetCompleted` 6 / `get_Completed` 7 /
  `GetResults` 8) awaited by polling `IAsyncInfo` `{00000036-0000-0000-C000-000000000046}`
  slot 7 `get_Status` (slot 8 `get_ErrorCode` on failure), then `GetResults`.
- `IVectorView<Radio>` — slots used: `GetAt` (6), `get_Size` (7).

The IIDs and vtable orders above are the metadata-assigned values for the
`Windows.Devices.Radios` contract, taken from the generated Windows metadata bindings
(`windows` 0.61.3, `src/Windows/Devices/Radios/mod.rs`; `IRadio_Vtbl` field order is
`SetStateAsync, StateChanged, RemoveStateChanged, State, Name, Kind`; `IRadioStatics_Vtbl` is
`GetRadiosAsync, GetDeviceSelector, FromIdAsync, RequestAccessAsync`). Enum values:
`RadioKind {Other 0, WiFi 1, MobileBroadband 2, Bluetooth 3, FM 4}`,
`RadioState {Unknown 0, On 1, Off 2, Disabled 3}`,
`RadioAccessStatus {Unspecified 0, Allowed 1, DeniedByUser 2, DeniedBySystem 3}`.

Fail-closed rules in the implementation: an unexpected `HRESULT`, a radio whose
`GetRuntimeClassName` is not `Windows.Devices.Radios.Radio`, an unknown async status, a
`dwNumberOfPhys` above 64, or a radio-state buffer shorter than `4 + n*12` all surface as
`Unsupported`/`ChannelUnavailable` instead of a value read from a wrong slot.

`wlanapi.dll` (`Win32_NetworkManagement_WiFi` bindings): `WlanOpenHandle(2)`,
`WlanEnumInterfaces`, `WlanQueryInterface(opcode 4 | 6)`, `WlanFreeMemory`, `WlanCloseHandle`
(read-only; no `WlanSetInterface` call is made — the write path is WinRT, one owner).
`iphlpapi.dll`: `GetAdaptersAddresses(AF_UNSPEC, GAA_FLAG_INCLUDE_GATEWAYS|GAA_FLAG_SKIP_ANYCAST)`
for the session-cut guard only.

Linux: the command is registered and the Linux platform attaches an explicitly unsupported radio
service, so `radio status` reports `Unsupported` on Linux rather than appearing to be silently
absent.

### 4.1 Dry run and the mutation gate

`RadioControl::radio_set_state` takes `ApplyMode`, and `RadioTransition` carries that mode plus an
`Option<RadioState>` observation, so "no write happened" is representable instead of being faked as
an observation. With `--dry-run` the Windows implementation stops after reading the target radio's
current state: it never reaches `SetStateAsync`. The session-cut guard still runs first, so
`--dry-run radio off wifi` from a remote session reports the refusal the commit would hit rather
than a plan. `radio off`/`radio on` are in the CLI's mutating set, so a commit runs the
vendor-conflict preflight and the `--yes` gate exactly like other device mutations, while a dry run
skips that preflight.

## 5. Session-cut guard (fail-closed)

Turning a radio off over a remote session can sever that session: on this unit the Wi-Fi
interface owns the only default route and the Tailscale session rides it. Therefore
`radio off` evaluates a guard **before** any write and refuses by default:

- Inputs: `SSH_CONNECTION` / `SSH_CLIENT` from the environment (peer and local address), and the
  per-interface facts from `GetAdaptersAddresses` (name, description, `IfType`, unicast addresses,
  gateway presence).
- Refuse (naming the interface) when the radio being switched off owns an interface that is
  either (a) the interface of the session's **local** address, or (b) an **up** interface that
  holds a **gateway** (i.e. owns a default route) — unless `--force` is passed. `--force` exists
  for an operator who has out-of-band access to the machine.
- Media mapping is by `IfType` only: `71` = 802.11 → Wi-Fi radio, `243`/`244` = WWAN → mobile
  broadband radio. Bluetooth is **not** guarded (parent decision for this wave): a Bluetooth PAN
  session is a residual, documented risk rather than a blocked operation.
- If no remote-session environment is present the guard does not fire (an interactive user
  switching off their own radio is not a session-cut risk).

Live relevance today: `radio off wifi` on this unit would refuse unless `--force`, because
ifIndex 36 (`WLAN`) both owns the session path and holds the 0.0.0.0/0 gateway.

## 6. What is implemented versus what was observed (unrun acceptance)

Observed live (read-only + the Bluetooth write in §2.2):
`radio status` inputs — WinRT enumeration, per-PHY Wi-Fi soft/hard state, adapter/gateway facts.

**Not run, and therefore not claimed:**
- `radio off wifi` / `radio on wifi`: the write path is implemented (same `SetStateAsync` call
  proven on Bluetooth), the read-back and previous-state rollback are implemented, but the Wi-Fi
  transition was **not** executed because it would cut the only path to the machine. It must be
  exercised with out-of-band access before anyone calls it accepted.
- Non-elevated execution: the observed session was elevated. Radio access is a per-application
  consent (`RadioAccessStatus`), so no administrator requirement is expected, but this was not
  measured.
- `Disabled` (`RadioState=3`, hardware/policy disabled): not reproducible without changing the
  BIOS `WirelessLAN`/`Bluetooth` gates; the mapping is a direct enum pass-through and is
  unobserved.
- The shipped Rust module itself: the ABI was proven from a raw probe (§2.5) and the written
  logic is Go/No-Go inspected, but this worker does not run builds or tests. Nothing in this
  document is a compiled-and-executed receipt for `vantage radio …`; the parent owns that run.

## 7. Lifecycle and authority

- No vendor process, driver, or service is started, attached, or emulated. COM/WinRT is
  initialized per call (`RoInitialize(MTA)` → RAII `RoUninitialize`) and every interface is
  released before returning.
- The write is a single `SetStateAsync` on one radio object, verified by read-back; on a mismatch
  the previous state is restored by the same call and the command fails with `VerifyMismatch`
  describing both the observation and the rollback outcome.
- `docs/05-bios-settings.md` already exposes the `WirelessLAN`/`Bluetooth` BIOS gates: those are
  the *hard* layer and remain a BIOS write with a reboot, not part of this channel.
