## 3. Axis B: documented but not parseable / not what the docs say

**B1. `audio noise-cancel ... farfield`** — documented three times, not a value.
`docs/04-peripherals.md:27`, `docs/08-architecture.md:80`, `docs/10-config-schema.md:69` all list
`{off|single|shared|spatial|voice-id|farfield}`. `pub enum NoiseCancelArg` (`lib.rs:1380-1386`) has
`Off|Single|Shared|Spatial|VoiceId`, and the domain type `NoiseCancellationMode`
(`crates/lctrl-core/src/audio.rs:68`, mapping test `crates/lctrl-core/tests/peripherals_contract.rs:159-176`)
has the same five. `vantage audio noise-cancel farfield` therefore exits 2 with clap's
"invalid value ... possible values: off, single, shared, spatial, voice-id". Owned by the doc-truth
worker per parent; do not "fix" by adding a variant — no raw code exists for a sixth mode.

**B2. docs/03 documents a different `perf` grammar than the CLI implements.** `docs/03-thermal-performance.md`:

| documented form | line | parse result |
|---|---|---|
| `vantage perf pl1 [get \| set <mW>]` | 604 | **fails**: `pl1` takes one positional `u32` (`lib.rs:738-740`); `get`/`set` fail `InvalidDigit` in clap |
| `vantage perf pl2 [get \| set <mW>]` | 605 | same |
| `vantage perf dbdc [get \| set <thr> <mA>]` | 606 | `set` **fails**: only `DbdcCommand::Get` exists (`lib.rs:764-767`) |
| `vantage perf oc cpu\|gpu\|mem ...` | 25, 607-609 | **fails**: no `oc` subcommand; `perf gpu status` is the implemented read (`lib.rs:770-773`) |
| `vantage perf mode set performance` | 740 | **fails**: `perf mode <value>` is positional (`lib.rs:726-729`), `set` is parsed as the mode value |
| `vantage perf pl1 set 15000` / `perf pl1 restore` | 741-742 | **fails**: same positional-watts shape; no `restore` |

The same file also uses the correct shapes elsewhere (its own L24 `vantage perf pl1`/`pl2`/`dbdc`
grouping and the 08 §2 tree's `perf mode {auto|cool|performance|geek}`), so this is stale spec prose,
not a design claim. The only genuinely missing capability in B2 is `perf oc` and `perf dbdc set`.

**B3. README documents a binary path that does not exist.** `README.md:117`:
"养护模式另经生产 CLI `conservation --dry-run` → `--yes --auto-restore` 验证". There is no

"unrecognized subcommand". The historical receipt it links
(`docs/evidence/conservation-cli-native-20261102.md`) is not affected; only the README sentence is.

**B4. `bios save` is documented as a committing command and always refuses.** 08 §2 tree L84 lists

(`execute_bios`). `bios set <name> <value> --save` is the path that actually commits (C29 receipts).
`bios discard` and `bios defaults` are implemented.

**B5. `sense reset` is implemented but `interfaces.md` says op 7 is not exposed.**

### 4.3 Global `--dry-run` is shadowed in three subtrees (safety defect)

`--dry-run` is declared `global = true` (415) and README L44/L172 present it as applying to writes.
Three subcommands declare their **own** `--dry-run` with the same arg id, which makes clap skip
propagating the global (clap_builder 4.6.7 `command.rs:4754-4762`: "already exists" → `continue`):

| subcommand | local flag | consumer |
|---|---|---|
| `fix run` | `FixCommand::Run { dry_run }` (617) | arm at 1853 passes the local value to `execute_fix_run(.., dry_run)` (6237) |
| `scene test` | `SceneCommand::Test { dry_run }` (635) | arm at 1864 passes the local value to `execute_scene_test(.., dry_run)` (6298) |
| `update local-driver apply\|rollback` | 1199, 1234 | `execute_local_driver` (6015) has **no** `ApplyMode`/`cli.dry_run` parameter at all |

`execute_with_services` computes `local_dry_run` only for `tune profile apply` (1587-1599), so
`apply` never covers these three. Concretely: `vantage --dry-run update local-driver apply <inf> <hwid>`
parses with `Cli::dry_run = true`, and `execute_local_driver` still builds `ApplyMode::Commit` because
it only reads the local `dry_run` field — the documented "global" preview does not reach the driver
installer. `update local-install` does not have this problem (§4.1), which makes the asymmetry visible
to users. Parent has assigned a dedicated behaviour item; **do not** treat this as a doc fix.

## 7. Divergence dossier handed to the `--dry-run` worker

1. `Cli` (`lib.rs:401-427`): `--dry-run` is `global = true`.
2. `execute_with_services` (`1564-1599`): `local_dry_run` is computed **only** for
   `TuneCommand::Profile { command: Some(ProfileCommand::Apply { dry_run: true, .. }) }`.
3. `execute_local_driver(local_update, command)` call (`5928`) and definition (`6015`): no
   `ApplyMode`, no `cli.dry_run`; `ApplyMode::Commit` whenever the local `dry_run` is false.
4. `execute_fix_run(machine_fix, issue, dry_run)` (`6237`) and `execute_scene_test(scene, event,
   rule, dry_run)` (`6298`): only the local field.
5. clap 4.6.7 `command.rs:4754-4762` is why the global flag cannot rescue this: a subcommand that
   already defines the id is skipped during global propagation, and the top-level `Cli.dry_run`
   is a different `ArgMatches` entry.
6. Required negative control (on the target, by whoever owns the fix): with a throwaway signed
   `.inf` that binds nothing, run `vantage --dry-run update local-driver apply <inf> <hwid>` and
   assert the device is unchanged and the report says dry-run; the same for
   `vantage --dry-run fix run <issue>` and `vantage --dry-run scene test <event>`. A read-back of the
   affected PnP/service state plus the command's own `mode` field is the minimum evidence.
7. Do not "fix" this by deleting the local flags without checking callers: `ProfileCommand::Apply`
   already merges both (`lib.rs:1595`, and the profile path ORs the two again), which is the shape
   the other three should adopt.
