# GPU overclock (GPU-OC) channel — vendor contract and 21VG verdict — 2026-11-05

Target: `TB14P-EZRA` (Lenovo 21VG, ThinkBook 14 G8+ IPH), BIOS `SWCN22WW`
(2026-07-15), serial `YX0JGHX9`, Windows 11 build 26300. Session: read-only.
No `Set*` method, registry value, driver state or BIOS variable was written.

Scope: recover the GPU-overclock method family (`Get/SetGpuOCMode`, GPU
clock/offset, GPU TGP/DBDC) from the provider and the Lenovo binaries, decide
which verbs actually return data on this SKU, and back the reachable read with
`perf gpu status`.

## 1. Verdict

The only GPU-OC verb that answers on this machine is the support probe. There
is no readable OC parameter block, no clock/offset read, no TGP read, and no
documented reversible setter. `perf gpu status` therefore reports
`supported: false` plus the provider's own verdict for the missing parameter
block, and the write side stays `Unsupported`.

| channel | live result (verbatim provider answer) |
|---|---|
| `LENOVO_GAMEZONE_DATA.IsSupportGpuOC` | `ReturnValue=True`, `Data=0` |
| `LENOVO_GAMEZONE_GPU_OC_DATA` (13 declared properties) | query → `0x8004100C` `WBEM_E_NOT_SUPPORTED` ("不支持"), no instance |
| `LENOVO_GPU_OVERCLOCKING_DATA` (15 declared properties) | query → `0x8004100C`, no instance |
| `LENOVO_GPU_METHOD` (0 methods declared) | query → `0x8004100C`, no instance |
| every other `LENOVO_GAMEZONE_DATA` method (51 of 52; 21 re-exercised here, the rest already recorded in `evidence/wmi-capability-exhaustion-20261104.md`) | `0x8004100F` `WBEM_E_INVALID_OBJECT` ("无效的对象") |
| `LENOVO_GAMEZONE_CPU_OC_DATA`, `LENOVO_CPU_OVERCLOCKING_DATA`, `LENOVO_MEMORY_OC_DATA`, `LENOVO_DISCRETE_DATA` | `0x8004100C`, no instance |

There is **no** `GetGpuOCMode` / `SetGpuOCMode` method on this interface at all,
and no GPU TGP property in any OC class. The `LENOVO_GAMEZONE_DATA` class
declares exactly 52 methods; the OC-related ones are:

```text

SetIGPUModeStatus(mode, Data)   NotifyDGPUStatus(status,Data) GetDGPUHWId(Data:String)

GetMemoryOCInfo(Data)           IsChangedYLog(Data)          GetHardwareInfoSupportVersion(Data)

```

`IsSupportGpuOC` is the only one that answers; all the rest return
`WBEM_E_INVALID_OBJECT`. (The remaining 34 methods are the fan, lighting,
key-lock, touchpad, thermal-mode, charge-mode, macro-key and GSync/water-cool
verbs; they answer the same way, already recorded in
`evidence/wmi-capability-exhaustion-20261104.md`.)

## 2. Provider identity

`Get-CimClass` reports for every GPU/OC class:

```text
provider = WmiProv            dynamic = True     WMI = True
LENOVO_GAMEZONE_GPU_OC_DATA       guid {887B54E2-DDDC-4B2C-8B88-68A26A8835D0}  "Definition of GPU OC parameter list"
LENOVO_GPU_OVERCLOCKING_DATA      guid {8A8984E2-228F-685F-B496-DDA5F52CBE5B}  "Definition of GPU OC parameter list"
LENOVO_GPU_METHOD                 guid {da7547f1-824d-405f-be79-d9903e29ced7}  "LENOVO_GPU_METHOD class"
LENOVO_GAMEZONE_DATA              guid {887B54E3-DDDC-4B2C-8B88-68A26A8835D0}
```

`WmiProv` is the Microsoft ACPI-WMI mapper (`wmiacpi.sys` 10.0.26100.1150,
running, start=Manual); the single live instance is
`ACPI\PNP0C14\GMZN_0`. There is no Lenovo user-mode WMI provider DLL behind
these classes — the method semantics live in the firmware's ACPI control
methods, so the "provider binary" is the ACPI table image, not a file that can
be string-scanned on this machine. `root\Lenovo` does not exist (`无效命名空间`).

Consequence for the wrapper: the classes are the contract. Their declared
property/parameter lists (observed live, §5) are the only schema that exists,
and a class with no instance is a hard firmware `不支持`, not a permissions or
binding problem — the same provider answers `LENOVO_GAMEZONE_DATA` queries in
the same session (§6 control).

## 4. Support-probe semantics, and a pre-existing inversion in this repo

`IsSupportGpuOC` answers `ReturnValue=True` (execution status) and `Data=0`
(the answer). `Data = 1` means supported, `Data = 0` means absent — stated in
`docs/01-hal-interfaces.md:154` ("`1` 支持 / `0` 不支持"),
`docs/03-thermal-performance.md:222` (`Data: 0`=不支持, `1`=支持) and
`:778` (`ENOTSUP` when `IsSupport*=0`). Independent live corroboration for this
machine: the OC parameter class is uninstantiated (`0x8004100C`), the GPU
method class declares no methods, there is no `VEN_10DE` device, and the
vendor OC whitelist has no entry for the installed Intel adapter.

**Pre-existing defect fixed in this change:** `GameZone::is_supported()`
(`crates/lctrl-hal-win/src/gamezone.rs`) decoded the probe as
`data == 0`, and `crates/lctrl-hal-win/tests/gamezone_client.rs`
(`support_probe_uses_zero_for_supported`) asserted that inverse. Nothing in the
specifications supports "zero means supported", and the string-scan and live
probe above contradict it; with the old decoder this SKU would have been
reported as GPU-OC-capable. The decoder is corrected to `data == 1` and the
test renamed to the documented polarity. The only other use is this new
`perf gpu status` read, so the fix is local to the OC slice.

### 5.1 GPU TGP / DBDC search result

String search over the OC binaries for `GpuTgp`, `GPUTGP`, `TGP` returned no
GPU power-limit symbol. The only TDP-shaped symbols in the scanned vendor
payload are PCManager's `SetGpuTDPWithSMFAN_DT` /
`SetGpuTemperatureWithSMFAN_DT` exports (a desktop SMFAN path, not a WMI
verb), and `DBDC` matches only inside unrelated binaries (BouncyCastle crypto,
the `SIO8786` EC widget) — i.e. substring false positives. The only DBDC
report is `LENOVO_REPORT_DBDC_DATA`, the battery discharge table that
`perf dbdc get` already reads. There is no GPU TGP/DBDC read to implement.

## 7. Implemented read — `perf gpu status`

Backed by `WindowsGpuOc` (`crates/lctrl-hal-win/src/gpu_oc.rs`) behind the
read-only `GpuOcControl` trait:

1. `LENOVO_GAMEZONE_DATA.IsSupportGpuOC` → `supported` (`Data == 1`) plus the
   raw probe (`method`, `return_value`, `data`).
2. `SELECT * FROM LENOVO_GAMEZONE_GPU_OC_DATA` (verbatim the vendor query):
   - row present → `parameter` with the 11 numeric properties of the 13
     declared ones, names verbatim, **no units and no physical meaning
     assigned** (the vendor config treats the same numbers as NVAPI clock
     offsets, which is not established for the WMI field);
   - `WBEM_E_NOT_SUPPORTED` / no row → `parameter: None` and
     `parameter_error` carrying the provider verdict (the `LctrlError`
     `Display` text, e.g. `feature is unsupported: ROOT\WMI query …`).
   - more than one row → refused (`parameter: None` plus the row count in
     `parameter_error`): the recovered contract describes one OC parameter
     block, and which device a second row would describe is not established.

No write command is added: no documented reversible set with readback exists on
this interface (no setter method, no OC parameter block, no verified
firmware-rejected-write path), and the vendor's own writes go through NVAPI or
the Intel OC SDK, neither of which is a channel this project may ship.

## 8. Non-claims

- No GPU clock, offset, TGP, power-limit or temperature read: `GetGPUTemp`
  returns `0x8004100F`, and no OC class has an instance.
- No `GetGpuOCMode`/`SetGpuOCMode`: the method does not exist in the class.
- The `parameter` decode is exercised only against a scripted transport, never
  against a machine that publishes one; it is a schema-faithful read, not an
  observed value.
- `IntelOverclockingSDK.dll`, `nvpowerapi.dll`, `SEGPUOCPlugin.dll` are not
  loaded, called, copied or redistributed; only their on-disk strings were read.
- Nothing was written: no WMI `Set*`, no registry value, no driver state, no
  BIOS variable.

## 9. Reproducibility

Probe scripts ran from `C:\Users\ezra\gpuoc-p{1..8}.ps1` on the target and wrote
`gpuoc-p{1..8}.txt`; they are read-only PowerShell (`Get-CimClass`,
`Get-CimInstance`, `Invoke-CimMethod` on `IsSupportGpuOC` only, file/registry
reads). The GPU-OC plugin tree was inspected with a bounded string extractor,
not executed.
