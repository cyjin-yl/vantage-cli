## 2. What the daemon actually is today (source inventory)

Binary: `vantaged` (`crates/vantage-daemon/Cargo.toml:15-17`), library `vantage_daemon`
(`crates/vantage-daemon/Cargo.toml:12-13`). It is a workspace member (`Cargo.toml:2`) and both CI workflows
copy it next to `vantage` (`.github/workflows/ci.yml:45-51`, `.gitea/workflows/ci.yaml:66-80`), so the delivered
artifact set is `vantage` + `vantaged` + `vantage-gui`.

### 2.1 Process shape (`crates/vantage-daemon/src/main.rs`)

1. `main()` (`main.rs:8-16`) creates an `mpsc` channel, calls `spawn_event_source`, then `vantage_daemon::run(receiver)`.
   Any error is printed to stderr and the process exits with the `LctrlError` exit code.
2. **Linux** event source (`main.rs:18-49`): one thread, `lctrl_hal_linux::LinuxHal`, an infinite 2 s poll loop that
   composes a snapshot of `hardware_info`, `capabilities`, `adapter_info`, `charge_mode`, `performance_state`,
   `fan_mode`, `active_power_scheme`, `detect_magicbay` and emits a `snapshot_changed` event **only when the JSON
   snapshot differs from the previous one**. Per-field failures are serialized as the error report (`value_or_error`,
   `main.rs:114-124`), not as a daemon failure.
3. **Windows** event source (`main.rs:52-73`) is two sources:
   - `spawn_windows_snapshot_source` (`main.rs:76-109`): the same 2 s diff-poller over `hardware_info`,
     `capabilities`, `performance_state` (P0 registry), `active_power_scheme` (P0 power API), `detect_magicbay`.
   - a native WMI event subscription (`main.rs:54-73`): `NativeWmiEventSource::subscribe(DOCUMENTED_LENOVO_EVENT_CLASSES)`
     → `vendor_event` per raw WMI event. Class list: `crates/lctrl-hal-win/src/events.rs:13-25`
     (`LENOVO_AC_PD_EVENT`, `LENOVO_AI_CHIP_EVENT`, `LENOVO_AI_SCENARIO_TYPE_EVENT`, `LENOVO_BTKBD_EVENT`,
     `LENOVO_DISPATCHER_EVENT`, `LENOVO_GAMEZONE_{FAN_COOLING,KEYLOCK_STATUS,LIGHT_PROFILE_CHANGE,POWER_CHARGE_MODE,
     SMART_FAN_MODE,SMART_FAN_SETTING,THERMAL_MODE}_EVENT`). If the subscription fails, the source thread prints
     `native WMI event source stopped: …` to stderr and ends; the daemon keeps serving snapshots.
4. Event kinds are exactly two constants (`crates/vantage-daemon/src/lib.rs:11-12`): `snapshot_changed`,
   `vendor_event`. `DaemonEvent::vendor_wmi` (`lib.rs:82-107`) reduces a raw WMI event to
   `{source_class, instance}` with the vendor `TIME_CREATED` left inside `instance` and the envelope timestamp
   set to the event's own `timestamp_unix_ms`.

### 2.2 The only automation the daemon performs (Windows only)

`crates/vantage-daemon/src/windows.rs:119-176`: for each `vendor_event`, the daemon calls
`NativeScenePolicy::match_event(source_class)`; each matched rule is applied with `ApplyMode::Commit`, and the
outcome is displayed through `NativeOsd::show(["scene <id>", "<action>", "applied|unavailable"])`. Actions are
`SetPowerScheme`, `SetPanelRefresh`, `SetFanMode`, `SetPerformanceMode` (`windows.rs:131-150`). Match/apply errors
are swallowed (`if let Ok(report)`) — an unavailable scene action is reported only as `unavailable` in the OSD.
There is **no** tune-engine trigger, no profile application, no rollback record, and no external-overwrite
detection in the daemon today, i.e. only half of §4.2 item 1/2 exists.

### 2.3 IPC server

Request/response schema (`lib.rs:16-35` for the request/response envelopes, `lib.rs:108-124` for `DaemonStatus`):

```jsonc
{"op":"status"|"stop"|"subscribe"}                     // DaemonRequest, tag = "op"
{"ok":true,"data":{…}} | {"ok":false,"error":"…"}      // DaemonResponse
// status data = DaemonStatus:
{"protocol_version":1,"version":"0.1.0","pid":1234,"started_at_unix_ms":…,"subscribers":0,"last_events":[…]}
```

- `PROTOCOL_VERSION = 1` (`lib.rs:9`), `MAX_EVENTS = 64` (`lib.rs:10`), `VERSION` (`lib.rs:14`).
- **Linux** (`unix.rs:92-184`): stale-socket probe then `bind`, socket mode `0600`, non-blocking accept loop with a
  25 ms idle sleep and a 25 ms cadence (≈40 wakeups/s), each accepted connection handled **inline** in the accept
  loop with a 2 s read timeout, request line limited to 64 KiB (`unix.rs:213-243`), peer verified with
  `SO_PEERCRED` uid equality (`unix.rs:264-296`). `Subscribers` is an unbounded `Vec` of 8-slot `SyncSender`s;
  `broadcast` (`unix.rs:245-250`) drops a subscriber whose queue is full or disconnected.
- **Windows** (`windows.rs:96-234`): named pipe created with `PIPE_REJECT_REMOTE_CLIENTS`,
  `PIPE_UNLIMITED_INSTANCES`, 64 KiB buffers and SDDL `D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;GA;;;OW)`
  (`windows.rs:450`), i.e. SYSTEM + Administrators + owner only; max 32 concurrent clients and max 16
  subscribers (`windows.rs:236-237`); one thread per client; `stop` also pokes the listener with a throw-away
  `CreateFileW` so `ConnectNamedPipe` returns (`windows.rs:302-320`).
- The server has **no persistence and no log**: neither `unix.rs::run_at` nor `windows.rs::run` opens a file to
  record state or failures, and `start_daemon` in `vantage/src/main.rs` spawns the daemon with stdin/stdout/stderr
  on `Stdio::null()`, so `eprintln!` output (e.g. "native WMI event source stopped") is discarded.

### 2.4 CLI wiring (real, but thin)

- `vantage/src/main.rs` `handle_daemon_command` intercepts `Command::Daemon{Some(_)}` in the platform binary
  **before** any HAL is constructed; `execute_daemon_command` dispatches `status`, `stop`, `start`, `install`.
  Interception happens in all three `main()` variants. Function names are the stable citation here — this file is
  shared, so its line numbers move with sibling work.
- Before this change `status` was `daemon_request(Status, "daemon status")`: a raw IPC forward that returns
  `ChannelUnavailable` (exit 4) whenever nothing is listening, prints the constant human line `daemon status`, and
  exposes no daemon version, no autostart/service state and no error field.
- Binary discovery: `daemon_binary` reads `VANTAGE_DAEMON_BINARY`, else `vantaged[.exe]` beside the running
  `vantage` executable.
- `start_daemon` probes `status` first, spawns the daemon detached-ish, then polls `status` 40 × 50 ms. On Windows
  `configure_detached` sets `CREATE_NEW_PROCESS_GROUP | DETACHED_PROCESS`; **on Unix it is a no-op** — the child
  keeps the caller's session and process group and therefore still receives terminal-generated signals (Ctrl+C).
- `install_daemon_platform` (Linux) writes `$XDG_CONFIG_HOME/systemd/user/vantaged.service` (default
  `~/.config/systemd/user/vantaged.service`) with `Restart=on-failure`, `NoNewPrivileges=true`,
  `WantedBy=default.target`, then `systemctl --user daemon-reload` + `enable` (no `--now`, no start).
  Windows registers the logon task `vantage-daemon` via `schtasks /Create /SC ONLOGON /RL HIGHEST /F` (requires an
  elevated caller). Other platforms: `Unsupported`.
- The shared library crate holds **no** daemon logic: `Command::Daemon` appears only in the capability registry
  (`crates/vantage-cli/src/capability.rs:151-157` state layer, `:718-730` command ids) and in the catch-all note
  `"daemon commands are handled by the platform binary"` (`crates/vantage-cli/src/lib.rs:7578`).

## 3. `vantage daemon status` — implemented surface

Motivation: the status query must answer with the daemon's own state *and* the reason it cannot be reached, without
pretending a missing daemon is a command failure or inventing a service manager reading it cannot get.

### 3.1 New daemon-side API (`crates/vantage-daemon`)

- `pub const VERSION: &str = env!("CARGO_PKG_VERSION")` — the daemon build's crate version.
- `DaemonStatus.version: String` with `#[serde(default)]` — additive to protocol 1; an older daemon that omits the
  field still parses, and a new daemon that emits it does not break an older client.
- `pub enum StatusProbe { Running(DaemonStatus), Absent{detail}, Fault{detail} }`, plus
  `probe()` / `probe_at(endpoint)` (Unix; mirrors `request_at`) / `endpoint_text()`.
  - `Running` — the daemon answered `Status` with `ok:true` and a parseable payload.
  - `Absent` — nothing is listening: Unix `NotFound`/`ConnectionRefused` from `connect`, Windows
    `WaitNamedPipeW` → `ERROR_FILE_NOT_FOUND` (2).
  - `Fault` — the endpoint exists but the exchange failed (peer-uid rejection, protocol/JSON error, `ok:false`,
    Windows `ERROR_PIPE_BUSY`/access-denied/other). Presence is then genuinely unknown and is reported as such.
- `probe` does not create state: no socket, no pipe, no thread, no file.

### 3.2 CLI output contract (`vantage daemon status [--json]`)

```jsonc
{
  "running": true,
  "endpoint": "\\\\.\\pipe\\vantage.sock",
  "cli_version": "1.0.0",
  "cli_protocol_version": 1,
  "protocol_matches": true,         // null when not reachable; daemon vs CLI IPC schema
  "daemon": {                       // null when not reachable
    "protocol_version": 1, "version": "0.1.0", "pid": 4212,
    "started_at_unix_ms": 1762340000000, "subscribers": 0,
    "last_events": [ {"ts_unix_ms": 1762340123456, "kind": "snapshot_changed", "payload": {…}} ]
  },
  "uptime_ms": 120000,              // null when not reachable; now - started_at_unix_ms
  "event_count": 3,                 // null when not reachable; length of the 64-event ring
  "last_event": {"ts_unix_ms": …, "kind": …, "payload": …},   // null when the ring is empty
  "autostart": {"kind": "logon-task" | "systemd-user-unit" | "unsupported",
                "path": "C:\\Windows\\System32\\Tasks\\vantage-daemon",
                "installed": true, "enabled": null,
                "note": "the task record exists; its enabled state is not inspected"},
  "observed_error": null,           // string when the daemon is unreachable / refused
  "observed_error_scope": "this status invocation only; the daemon keeps no log"
}
```

Exit codes: `Absent` → success (exit 0, `running:false`, `observed_error` = the connect detail) because "no daemon"
is a normal, honest answer for a query; `Fault` → error `ChannelUnavailable` (exit 4) carrying the detail, because
an endpoint that exists but fails the exchange is a real fault a script must not treat as "merely stopped".
`stop`/`start`/`install` keep their existing error behavior.

Autostart evidence is filesystem evidence, not a service-manager call:
- Linux: unit file `$XDG_CONFIG_HOME/systemd/user/vantaged.service` and the enable symlink
  `$XDG_CONFIG_HOME/systemd/user/default.target.wants/vantaged.service` (`enabled`). Both come from
  `daemon_config_root()` / `daemon_unit_dir()` / `daemon_unit_path()` / `daemon_unit_enable_link()` and
  `DAEMON_UNIT_NAME`, and `install_daemon_platform` uses the *same* `daemon_unit_path()` and the same
  `DAEMON_UNIT_NAME` for `systemctl --user enable` — there is no second copy of the path.
- Windows: the task file `%SystemRoot%\System32\Tasks\vantage-daemon`, derived from `DAEMON_TASK_NAME`, which is
  also the `/TN` value `install_daemon_platform` passes to `schtasks`. `enabled` is **not inspected** (no task-XML
  parse, no `schtasks /Query` subprocess) and is reported as `null`.
- If neither `HOME` nor `XDG_CONFIG_HOME` resolves on Linux, `path` is `null` and the note says exactly that.

Human output (one line per observation, then the autostart record):

```
daemon: running
  endpoint: \\.\pipe\vantage.sock
  version: 0.1.0 (protocol 1)
  pid: 4212
  uptime: 2m00s
  subscribers: 0
  buffered events: 3/64
  last event: snapshot_changed at 1762340123456 (unix ms)
  autostart: logon-task at C:\Windows\System32\Tasks\vantage-daemon (the task record exists; its enabled state is not inspected)
```

With nothing listening the first group becomes `daemon: not running` / `endpoint:` /
`last error: <detail> (observed by this status call; the daemon keeps no log)`, and a protocol mismatch appends
`warning: the daemon speaks protocol N, this CLI speaks M`.

`observed_error` semantics, stated plainly and carried by the field name plus the sibling `observed_error_scope`
string (the human output says "observed by this status call; the daemon keeps no log"): it is **what this
invocation observed** — the connect/pipe detail, or the daemon's own `error` string when it answered `ok:false`.
The daemon persists no log, so a failure from an earlier daemon lifetime is not recoverable here.

### 3.3 What the surface should expose, and where each part stands

| Surface | What it must expose | State after this change |
|---|---|---|
| status | presence, pid, uptime, subscriber count, buffered-event count, last event, endpoint, autostart record, and the error the query itself observed | implemented (§3.2) |
| version | the daemon crate version **and** the IPC protocol version, so a daemon left over from a previous binary is visible | implemented as `daemon.version`, `daemon.protocol_version`, `cli_protocol_version`, `protocol_matches`. A per-build identity (git hash/build stamp) is **not** implemented — inventing one from the crate version would be a fabricated fact |
| events | the newest 64 events plus a live stream of `snapshot_changed` / `vendor_event` | server side exists (`Status.last_events`, `Subscribe`); **no CLI consumer**, so the stream is not exposed |
| last error | why the daemon cannot be reached **and** why a previous start failed | first half implemented (`observed_error`); second half **not implemented** — the daemon writes no log (§4) |

## 4. Explicitly NOT implemented (and why)

The four headline gaps, so they are not lost in the table below: **(a)** no `vantage daemon events` subscriber —
the event stream is implemented server-side but has no CLI consumer; **(b)** no daemon-side tune trigger (only the
Windows scene-policy + OSD automation exists, nothing on Linux, and the daemon crate does not depend on
`lctrl-tune`); **(c)** no persisted daemon log, so `observed_error` cannot see an earlier daemon lifetime;
**(d)** Linux `daemon start` does not `setsid`, so the spawned daemon stays in the caller's session/process group.

## 5. Compatibility

- Protocol stays `1`; `version` is additive with `#[serde(default)]`, so mixed old/new daemon↔CLI pairs still parse.
- A daemon that omits `version` yields `daemon.version == ""`; `protocol_matches` is computed from
  `protocol_version` only, so an older daemon is still classifiable.
- **`daemon status --json` changed shape.** It used to emit the raw `DaemonStatus` object (`pid`,
  `started_at_unix_ms`, `subscribers`, `last_events` at top level) because `status` was a plain IPC forward. It now
  emits the report in §3.2 with the daemon's own status nested under `daemon` (`null` when unreachable), so a
  script keyed on `.pid` must read `.daemon.pid`. Nothing else in this workspace consumed the old document.
- `daemon.last_events` is still the full 64-event ring.
- No new threads, no service install, no write path, no environment variable was introduced by this change
  (it honors the existing `VANTAGE_SOCKET` / `VANTAGE_PIPE` / `VANTAGE_DAEMON_BINARY`).
- **Resolved conflict with another evidence doc:** `docs/evidence/error-paths-20261105.md` records
  `daemon status` → exit 4 `channel_unavailable` as the "reference pattern for an absent channel" (its §1 table row
  and its closing exit-code summary). Those two statements are stale after this change. Decision (coordinating
  agent, recorded here): keep `daemon status` at exit 0 with `running:false` — "is the daemon running?" is a state
  question, and absence is an answer — and have that document's "absent channel" reference point at
  `daemon start` / `daemon stop`, which act on a channel and do keep returning `ChannelUnavailable` when nothing
  answers. That document is owned by another worker and was **not** edited here; its owner fixes the two lines.

## 6. Authority and lifecycle

- Read-only: only filesystem `stat` of the unit file / enable symlink / task file, plus one IPC `Status` exchange.
- No hardware channel is touched; `daemon status` cannot change charge mode, performance mode, fan mode, or any
  registry/ACPI state. The Windows scene automation described in §2.2 is pre-existing behavior of the daemon, not
  something this change enables.

## 8. Acceptance for the parent (positive + negative controls)

Prerequisite: `daemon status` needs **no** `vantaged` binary — it only probes the endpoint. `daemon start` /
`daemon install` do need `vantaged[.exe]` next to `vantage[.exe]` (or `VANTAGE_DAEMON_BINARY`), and the Windows
logon-task install needs an elevated caller; both fail loudly when that is missing, which is not a status defect.

1. `vantage daemon status` with no daemon → exit 0, `running:false`, `endpoint` non-empty, `daemon:null`,
   `observed_error` containing the OS connect/pipe error; human output starts with `daemon: not running` and its
   `last error` line states that the daemon keeps no log.
   Negative control: it must **not** exit 4 and must **not** print `daemon status` as the only human line.
2. `vantage daemon install --dry-run` then re-run `status` → `autostart.installed` still `false` on Linux
   (`--dry-run` writes nothing), then `install` → `installed:true`, and `enabled:true` only after the enable
   symlink exists.
3. `vantaged` started manually (e.g. `VANTAGE_SOCKET=/tmp/t.sock vantaged`), then
   `VANTAGE_SOCKET=/tmp/t.sock vantage daemon status --json` → `running:true`, `daemon.pid` equals the daemon pid,
   `daemon.version == "0.1.0"`, `daemon.protocol_version == 1`, `uptime_ms >= 0`, and after a snapshot-change
   interval `event_count > 0` with `last_event.kind == "snapshot_changed"`.
4. Protocol back-compat negative control: feed the CLI a status payload **without** `version`
   (e.g. `printf '%s\n' '{"op":"status"}' | nc -U …` style stub, or a unit test on `DaemonStatus` deserialization)
   → parses, `daemon.version == ""`, no panic.
5. `Fault` control: a socket that accepts the connection but rejects the status request (the stub in
   `crates/vantage-daemon/tests/status_probe.rs::a_daemon_that_rejects_the_status_request_is_a_fault`) → `Fault`,
   and `vantage daemon status` exits 4 carrying the daemon's own error text. A **plain file** left at the socket
   path is deliberately *not* a fault: Linux returns `ECONNREFUSED` for a non-socket inode, which is classified
   `Absent` because nothing is listening — that is the intended reading.
6. Windows: `vantage daemon status` with no daemon → exit 0, `running:false`, `autostart.kind == "logon-task"`;
   with the pipe absent and `VANTAGE_PIPE` pointing at a garbage name → same shape (absent classification).
7. Unit tests that must stay green: `crates/vantage-daemon/tests/ipc_contract.rs`,
   `crates/vantage-daemon/tests/event_buffering.rs` (both deserialize `DaemonStatus` from `response.data` and must
   tolerate the new `version` field), plus the new `crates/vantage-daemon/tests/status_probe.rs` (Absent for a
   missing path, Running with `version`/pid/protocol from a real `run_at` server, Fault for a status rejection).
   The new file was written but **never executed** by this worker.
