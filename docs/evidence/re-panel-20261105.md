## 2. Overdrive contract (BiosOD.dll)

`BiosOD.dll` (PE32+ x64, image base `0x180000000`) exports four functions:

```text
0x180002180  Init
0x1800021a0  Uninit
0x1800021c0  GetODStatus   -> jmp 0x1800028f0 (this, bool*)
0x1800021e0  SetODStatus   -> jmp 0x180002c00 (this, bool)
```

Its import table is only `KERNEL32/ole32/OLEAUT32` (`CoCreateInstance`,
`CoSetProxyBlanket`, `SysAllocString`, …); it reaches the firmware through WMI
with a **late-bound, name-addressed** call chain. The UTF-16 string table
(`.rdata`) contains:

```text
0x18001e0e0  root\wmi
0x18001e0f8  LENOVO_OTHER_METHOD
0x18001e120  GetFeatureValue
0x18001e140  SetFeatureValue
0x18001e160  SELECT * FROM LENOVO_CAPABILITY_DATA_00
0x18001e1b0  IDs
0x18001e1b8  Capability
0x18001e1d0  __PATH
0x18001e1e0  IDs
0x18001e1e8  value
0x18001e1f4  "1"      0x18001e1f8  "0"
0x18001e088  "1703936"
```

`1703936` = `0x001A0000` is the overdrive feature identifier. The recovered
flow is:

1. **Capability gate** (`0x1800026f0`–`0x1800028d9`): execute
   `SELECT * FROM LENOVO_CAPABILITY_DATA_00`, walk the instances, read the
   `IDs` property and accept the row where `(IDs >> 16) == 0x1A`
   (`sar eax,0x10; cmp eax,0x1a` at `0x180002833`), then read `Capability`
   from that row and report `Capability != 0` as the support bit. No 0x1A row
   ⇒ overdrive is not supported, and `SetODStatus` never runs.
2. **Instance path**: read the `__PATH` property of the active
   `LENOVO_OTHER_METHOD` instance (`0x1800029f6`) and `ExecMethod` on it.
3. **Read** (`0x1800028f0`): `GetFeatureValue` with in-parameter `IDs`
   (`VT_BSTR "1703936"`), then read the returned `value` property and report
   `value != 0` (`0x180002b1c`).
4. **Write** (`0x180002c00`): `SetFeatureValue` with `IDs = "1703936"` and
   `value = "1"` (on) / `"0"` (off) — `0x18001e1f4`/`0x18001e1f8` selected by
   the bool argument at `0x180002d73`. The call's success is the method's
   `ReturnValue`; the vendor does **not** read the state back.

Live class shape (`Get-CimClass -Namespace root\WMI -ClassName
LENOVO_OTHER_METHOD`) confirms `GetFeatureValue`, `SetFeatureValue`,
`GetDataByCommand`, `GetDataByPackage`. `LENOVO_CAPABILITY_DATA_00` carries
`Active`, `IDs`, `Capability`, `DefaultValue`, `InstanceName`.

## 4. Super-resolution contract

### 4.1 IGCL leg (vendor plugin)

`SESuperResolutionPlugin64.dll` (image base `0x180000000`) exports
`GetAbility` (`0x6ef0`), `GetSRState` (`0x6f10`), `InitPlugin` (`0x6e30`),
`RegisterCallback` (`0x6ec0`), `SWRegisterLogCallback` (`0x6ed0`),
`SetSRState` (`0x7020`), `UnitPlugin` (`0x6eb0`). It binds IGCL by name at
runtime (`GetProcAddress`) — `ctlInit`, `ctlClose`, `ctlReservedCall`,
`ctlEnumerateDevices`, `ctlGetDeviceProperties`,
`ctlGetSupportedVideoProcessingCapabilities`,
`ctlGetSetVideoProcessingFeature` — and logs every step
(`ctlInit ret=%d`, `ctlGetSupportedVideoProcessingCapabilities:ret=%d`,
`ctlGetSetVideoProcessingFeature: SET g_SrMode = %d`,
`ctlGetVideoProcessingFeatureDetails set : flag %d, width %d, height %d`,
`SRFeature ret=%d`, `SRFeature_3_1:ret = %d`).

Capability enumeration (`0x180004f00`) is the documented **two-pass** shape:

1. `ctl_video_processing_feature_caps_t` with `Size = 0x58` (88),
   `NumSupportedFeatures = 0`, `pFeatureDetails = NULL` → returns the count
   (`[rbp-0x31]`).
2. Allocate `count` records of `0x78` (120 = `sizeof(ctl_video_processing_feature_details_t)`),
   pass the array back in the same struct → the driver fills `FeatureType`,
   `ValueType`, `Value`.
3. Query the feature of interest again with its custom value buffer
   (`0x74` = 116 = `sizeof(ctl_video_processing_super_resolution_info_t)`)
   bound to `pCustomValue`.

Get/set (`0x180004808`–`0x180004d33`) builds the 120-byte
`ctl_video_processing_feature_getset_t` and the vendor's layout matches the
public header and our Rust pinning exactly: `FeatureType` at `+8` (value 4 =
`CTL_VIDEO_PROCESSING_FEATURE_SUPER_RESOLUTION`), `bSet` at `+0x19`,
`ValueType` at `+0x1c` (5 = `CTL_PROPERTY_VALUE_TYPE_CUSTOM`),
`CustomValueSize` at `+0x28`, `pCustomValue` at `+0x30`. The custom payload is
the SR get/set struct with `super_resolution_flag` at `+8`; the plugin writes
`1` (`FLAG_DISABLE`) or `2` (`FLAG_ENABLE_DEFAULT_SCENARIO_MODE`) at
`0x1800048a8`/`0x180004928`.

The vendor's payload is allocated as `0x58` (88) bytes — the pre-`ReservedBytes[3]`
header shape — while the published 1.x header is 92 bytes. The driver accepts
the caller's `CustomValueSize`, so the Rust binding keeps the 92-byte public
layout (`crates/lctrl-hal-win/src/panel_features.rs` layout tests pin
`size_of(CtlVideoProcessingSuperResolution) == 92`, flag at offset 8, and
`size_of(CtlVideoProcessingSuperResolutionInfo) == 116`).

The plugin also maps a `g_SrMode` preset to the maximum input size the feature
may upscale from (`0x780×0x438`, `0x500→0x2d0×0x1e0`, `0x300→0x35a×0x1e0`,
`0x200→0x280×0x1e0`), and clears
`pCustomValueSet->super_resolution_max_in_enabled` when the mode is 0 or 2.

### 5.2 What this changes

The vendor does not use a Lenovo-private filter for eye care: it applies a
per-channel gamma ramp through the system GDI entry points. That makes the
feature implementable without any Lenovo payload, which is why
`lctrl-hal-win` now drives it directly:

- `GammaRampApi` / `NativeGammaRamp` in
  `crates/lctrl-hal-win/src/panel_features.rs` (`GetDC(NULL)` +
  `GetDeviceGammaRamp`/`SetDeviceGammaRamp`, windows-sys feature
  `Win32_UI_ColorSystem`);
- `WindowsPanelFeatures::with_gamma_ramp` attaches it (the constructor is
  unchanged, so a build without the transport reports
  `panel.eye-care.gamma-ramp-detached`);
- reads classify the live ramp; a ramp that matches no known level is reported
  as unknown (`Ok(None)`), never snapped to the nearest preset;
- writes capture the raw ramp, apply, read back and restore the captured ramp
  on mismatch (`LctrlError::VerifyMismatch`).

### 5.3 Levels

`eye_care_lut` maps `Off` to the identity ramp, `Mid` to 5000 K and `High` to
4000 K. Those two Kelvin values are **repo-inferred** (standard
Tanner-Helland approximation), not extracted from the vendor preset table:
the vendor's actual `BlueLightCutForOffice` / `BlueLightCutForReading` values
live in .NET IL constants and have not been recovered byte-exactly. The
capability row and the code comment say so; a byte-level comparison is the
next acceptance step before any claim of vendor equivalence.

While activating this path a real defect in `kelvin_channel_gain` was found
and fixed: the Tanner-Helland formulas are defined on **hundreds** of Kelvin
(`t = K/100`, branches at 6600 K and 1900 K). The previous code fed Kelvin
directly into the logarithms with a 4900 K branch, which clamped every channel
to 1.0 except blue (which it zeroed below 4900 K) — i.e. `mid` was a no-op and
`high` removed blue entirely. The corrected function yields R 1.0 / G 0.894 /
B 0.808 at 5000 K and R 1.0 / G 0.807 / B 0.652 at 4000 K.

### 5.4 Live verdict and why the row stays unsupported

The channel exists and is implemented, but this session cannot verify a
desktop gamma write: the SSH logon is a network logon (same class of
restriction as the MSR device, docs/evidence/wmi-capability-exhaustion-20261104.md
§10) and `SetDeviceGammaRamp` requires an interactive session. The registry
row therefore keeps `DispatchSupport::Unsupported` with the recovered owner
and the inferred-Kelvin caveat; promotion needs an interactive-session
acceptance run (`vantage panel eye-care high --dry-run`, then a commit with
readback), not a source-only argument.

## 6. Source changes derived from this evidence

`crates/lctrl-hal-win/src/panel_features.rs`:

1. `super_resolution_capability()` now performs the contract's two-pass
   enumeration (count with `pFeatureDetails == NULL`, then the allocated
   array, then the per-feature custom query) instead of one synthesised
   detail record. A successful enumeration that does not list
   SUPER_RESOLUTION reports `panel.super-resolution.feature-not-advertised`;
   a driver rejection surfaces as `ChannelUnavailable` with the raw result
   code. The count is bounded by `MAX_VIDEO_PROCESSING_FEATURES = 64`.
2. `set_super_resolution_flag()` is no longer a blanket refusal and no longer
   a blind write: it reads the full 92-byte payload first (previous flag plus
   the maximum-input limiter fields it must preserve), writes through the
   same get/set contract, then reads the payload back. A rejected read refuses
   the write (`panel.super-resolution.state-query.rejected`, the 21VG case);
   a readback mismatch restores the previous flag and reports
   `LctrlError::VerifyMismatch`. A no-op write (flag already at the requested
   value) sends nothing.
3. Registry rows: `PANEL_SUPER_RESOLUTION` now declares
   `Readback::Required` / `Rollback::PreviousState` (the implemented write
   contract) and the three panel rows carry the recovered owner verdicts
   instead of "not verified" placeholders.
4. Eye care: new `GammaRampApi` seam + `NativeGammaRamp`
   (`GetDC(NULL)`/`GetDeviceGammaRamp`/`SetDeviceGammaRamp`, windows-sys
   feature `Win32_UI_ColorSystem`), `WindowsPanelFeatures::with_gamma_ramp`,
   ramp↔LUT conversions, `classify_ramp` (unknown ⇒ `None`), and the
   guarded write described in §5.2. `kelvin_channel_gain` was corrected to
   hundreds-of-Kelvin (§5.3); the two level constants are still marked
   repo-inferred in the code comment.
5. `vantage/src/main.rs` attaches `NativeGammaRamp` when IGCL loads; the
   constructor is unchanged so existing composition/tests keep compiling.

Tests (`crates/lctrl-hal-win/tests/panel_features.rs`, Windows-only): added
covered write, refused-without-read, ignored-write, third-value-rollback and
dry-run cases against the scripted `IntelCtlApi` fake, plus an identity-ramp
read, unknown-ramp (`None`) read, applied-and-verified write, restore-on-
mismatch and dry-run cases against a scripted `GammaRampApi` fake.
